# 0.1.4 定向校准与验证边界（2026-10-22）

## 已有真实证据

- 用户截图显示内置豆包网页成功加载并登录，网页无法打开不再是当前阻塞。
- 用户提供的 0.1.2 结构诊断确认输入框为 `textarea[data-testid="chat_input_input"]`，但没有消息容器、发送和完成状态的充分证据。侧栏 `global-search-icon-entry` 是历史搜索，不能作为联网开关。
- 用户随后提供的 0.1.3 协议诊断捕获真实 `POST https://www.doubao.com/chat/completion`：HTTP 200、SSE 24 帧、9,454 字节，`invalidPayloads=0`、`partialFrame=false`、`truncated=false`、`transportEnded=true`。这是本次网页请求与网络响应的真实证据。
- 0.1.3 采集器把全部事件名降为 `other`、关键父字段降为 `[key]`，结构聚合还丢失事件顺序。已删信息不可恢复，现有诊断仍不足以实现准确请求或响应解析。
- 唯一已记录的白名单结束标记是嵌套数组中某块的 `is_finish=true`。它不能证明整条回答或业务任务完成，也不能证明登录状态可以用于后台请求。

## 本次改造范围

修正采集器：只针对实际观察到的 `/chat/completion` 进行定向校准，保留受限制的协议字段名、事件名和按原顺序记录的事件；用本次采集内一致的别名表达标识符等值关系。正文只记录长度、预设合成标记匹配和变化关系，不导出原始正文、ID、Cookie、请求头值或登录存储。

用户点击「开始校准」后，在同一测试会话按顺序手动发送「复制测试1」「复制测试2」提供的两条合成提示词。复制按钮仅写入本机剪贴板，程序不自动操作网页、发送或重放。最长 180 秒、最多 4 个目标请求；可以手动「结束并导出」，达到时间上限自动保存。旧任务队列始终保持暂停。

此次再次要求用户校准，是为修复上一版采集器丢失必要信息的问题，不是用户上次操作错误。协议字段、动态签名、任务绑定及整轮结束条件仍需要现场证据；后台直接调用尚未实现，也不承诺一次校准一定解决所有限制。HTTP 结束和局部结束标记始终只作为证据。

`npm test` 的 59 项测试全部通过。新增覆盖真实端点定向筛选、两轮 ID 别名一致性、事件原名与顺序、合成标记分片匹配、请求头事件乱序、控制值与嵌套 JSON 脱敏、受限 patch 路径，以及仅在用户点击时复制消息。代码测试使用合成事件；没有启动或操作真实豆包窗口。

Windows x64 / Electron 43.3.0 的 0.1.4 构建成功；包内 17 份源码与资源逐字节匹配，未包含用户目录、诊断文件、依赖或测试目录，常见密钥模式检查无命中。版本与依赖锁一致，UI 控件引用检查通过。

真实校准结果尚待用户按 [manual-test.md](manual-test.md) 的第一部分提供，不能以单元测试替代。未将用户的诊断文件或登录数据加入仓库。
